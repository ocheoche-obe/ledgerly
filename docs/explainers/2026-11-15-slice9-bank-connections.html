Background

Deep background — skip this layer if Plaid Link and Cognito are already familiar.

Plaid Link is a small app Plaid runs inside an iframe on your page. Your server asks Plaid for a short-lived link token; the browser opens Link with it; the user picks a bank and logs in at Plaid, never at Ledgerly; and Link hands the browser a one-time public token. The server swaps that for a long-lived access token, the real credential for one bank login, which Plaid calls an Item. Ledgerly keeps the access token in Secrets Manager and nowhere else, so the browser only ever holds the two disposable tokens.

server: link token
browser: Link iframe
public token
server: exchange
access token → Secrets Manager

Two Link behaviours matter for this PR. Update mode: when a bank login breaks (ITEM_LOGIN_REQUIRED), you mint a link token for the existing Item (pass its access token, no products). Link then only asks for the password, and returns no public token, because nothing needs exchanging; the old access token simply works again. Deleting and re-linking would instead create a second Item, billed separately. react-plaid-link wraps Link in a React hook, usePlaidLink({token, onSuccess, onExit}), exposing ready and open.

Cognito Hosted UI sessions. Signing in sets two sessions: tokens in the SPA's localStorage, and a cookie on Cognito's own domain. Logging out of only the first means the next "Log in" is silently answered by the cookie. Ending the second requires Cognito's /logout endpoint, which takes client_id and logout_uri, its own names, not the OIDC standard's.

Narrow background — the Ledgerly code. PR #61 built the backend: api_plaid (link token, exchange, sync start), the async plaid_sync worker (pulls /transactions/sync, writes ordinary TXN# rows plus categorization jobs), and per-Item PLAIDITEM# records (ADR-014). Everything downstream, from categorizer to cycles to dashboard, was untouched, as architecture §1.2 promised. This PR gives it a face, and on the way it hit two problems ADR-014 hadn't decided: loan payments counting as income, and fake Sandbox money inside the owner's real totals (ADR-015).

Intuition

The panel is a small state machine over one bank connection. Here is a single connection, First Platypus Bank, moving through it:

Connect bank
331 new
Sync now → 0 new
sync fails: ITEM_LOGIN_REQUIRED
Reconnect (password only)
Disconnect

The interesting idea is in the middle. Reconnect must open Link for the existing Item. The bug the first blind review caught: react-plaid-link keeps the previous handler and reports ready = true while a new token is still loading. The panel had swapped in the update-mode token and auto-opened on ready, so it opened the old new-connection handler. The user would have created a second Item at Plaid while the panel believed it was repairing the first, skipping the exchange, so the new Item's token would never be stored. The fix gives every token its own component instance, <LinkSession key={token}>, so ready can only ever describe that token.

The second idea is about what counts as spending. A loan account sees a $514 payment as money in (you owe less):

AccountRowAmountCounted?
Checking ••1000Auto loan payment−$514.00yes (the cash leaves here)
Auto loan ••5000Payment received+$514.00no, accountType = loan

Counting both sides nets to zero; counting only the loan side reads as income. So each Plaid row now carries its account's type, and the dashboard skips loan rows, saying how many it skipped rather than letting the totals quietly disagree with the list.

The third idea is separation. Sandbox data now belongs to a second, dev-only Cognito user, so the USER#<sub> partition (ADR-006) keeps it away from the owner's real rows. That needs no filter anywhere.

Code walkthrough

core/: the rules, AWS-free

plaid_items.py adds RECONNECT_ERROR_CODES (only ITEM_LOGIN_REQUIRED), so the view can say needsReconnect, plus account_types() and excluded_from_spend(txn). plaid_normalize.normalize stamps accountType, and it joins SOURCE_FIELDS (a Plaid modified may change it) and a new STICKY_SOURCE_FIELDS (it may never remove it). That stickiness took three review rounds to get right:

round 1: type read from the PLAIDITEM record   → disconnect deletes it → loans count again
round 2: type stamped on each row             → a closed loan drops out of /accounts/get → the next modified removes it
round 3: stored ∪ fresh types for one sync    → the stored list is replaced each sync → gone a sync later
final:   accountType is sticky in the update  → set, never removed

budgets.summarize skips excluded_from_spend rows and reports excludedCount. plaid_purge.plan_sandbox_purge decides which owner-partition records were Sandbox: TXN# with source=plaid and plaidEnv=sandbox, their PLAIDTXN# pointers, and their syncs. It refuses while any connection is linked, deletes pointers → syncs → rows (so a crash leaves a re-runnable state), and fingerprints the exact key set.

adapters/: Plaid and AWS calls

plaid.py: link_token_create(access_token=…) for update mode (no products), item_remove, sandbox_item_reset_login. secrets.delete_access_token refuses unless the stored entry's sub is the caller's. dynamo.py: set_plaid_item_error / REMOVE errorCode on success, delete_plaid_item, and the sticky-field rule in the update path.

functions/: thin handlers

api_plaid gains GET /plaid/items, DELETE /plaid/items/{itemId} and update-mode link tokens. Disconnect's order is the point: Plaid first (/item/remove; ITEM_NOT_FOUND means already gone), then the token, then the record. A failed remove changes nothing, so retrying is safe, and no Item is ever left live and billed with our side forgotten. plaid_sync records non-retryable Plaid errors on the Item. api_cycles is unchanged in shape, because the exclusion lives in summarize.

infra/

Two JWT-authorized routes and DELETE in CORS. PlaidSandboxUser is created only when the stage has Plaid; its logical ID contains "Plaid", so the existing CI check that prod has no Plaid resources covers it for free. ops/ is excluded from the Lambda asset.

frontend/

BankConnectionsPanel: pre-initialized Link, one keyed LinkSession per token, Sync now (polls the import, then reloads the dashboard at +20 s and +45 s while categorization runs), Reconnect, Disconnect, and syncErrorCopy, which gives every failure state a next step. The dashboard shows the pending share and the loan note. auth.ts builds Cognito's logout URL itself.

Deployed ≠ working, honoured. Everything above was run on the deployed dev stack through the real UI: connect (331 rows, 330 categorized), sync 0, forced login failure → Reconnect, disconnect, a second persona, and refresh-driven added/modified/merged. Two bugs only the real browser found: the logout, and a locked-account message with no way forward.
